# UC Print

A small tool for converting **Undercards decks and individual cards into print-ready physical cards**.

The goal is to make it easy to play Undercards casually as a physical tabletop card game without manually recreating every card.

The project should reuse live/current Undercards card data wherever practical, render cards at proper print resolution, and generate ready-to-print A4 PDFs.

---

# 1. Project Goal

Build a dedicated **Undercards Physical Card Exporter**.

Primary workflow:

```text
Paste Undercards deck code
        ↓
Decode deck
        ↓
Load current card data
        ↓
Load card artwork
        ↓
Render cards at print resolution
        ↓
Add required/generated/token cards
        ↓
Arrange cards on A4 sheets
        ↓
Export printable PDF
```

Secondary workflow:

```text
Search card library
        ↓
Select individual cards
        ↓
Choose quantity
        ↓
Export PNG or printable PDF
```

The tool should focus on:

* Accurate recreation of Undercards cards.
* High-quality physical printing.
* Minimal manual work.
* Supporting generated/token cards.
* Supporting complete deck export.
* Simple local operation.
* Avoiding unnecessary infrastructure.

This is intended primarily for **personal/non-commercial tabletop use**.

---

# 2. Why Build This

Existing Undercards tools are primarily designed for playing or displaying cards digitally.

The existing community card editor can render and download cards, but its renderer is designed for web-sized images rather than high-quality physical printing.

Current community tooling already demonstrates that Undercards exposes useful data such as:

```text
https://undercards.net/AllCards
```

Card artwork is also available through paths similar to:

```text
https://undercards.net/images/cards/<image>.png
```

Deck codes are simple Base64-encoded JSON structures containing information such as:

```json
{
  "soul": "...",
  "cardIds": [],
  "artifactIds": []
}
```

Because the underlying data is already accessible, we do not need to manually recreate the Undercards database.

The main task is therefore:

```text
Undercards Data
      +
Print-Quality Renderer
      +
Deck Parser
      +
PDF Generator
```

This makes the project relatively small compared to building a complete card-game editor from scratch.

# 3. Design Philosophy

The physical version should reproduce Undercards **1-to-1 whenever reasonably possible**.

Do NOT simplify mechanics unnecessarily.

Many effects translate directly to physical cards.

Examples:

```text
Deal 3 damage.
```

Works unchanged.

```text
Summon a Gaster Blaster.
```

Use a physical Gaster Blaster token card.

```text
Add a Gaster Blaster to your hand.
```

Take a Gaster Blaster card from the shared generated-card pool and place it in your hand.

```text
Transform into X.
```

Replace the original card with the appropriate generated/token card.

```text
Gain +2 ATK.
```

Use a counter/token.

```text
Silence a monster.
```

Place a Silence marker on the monster.

````

Only mechanics that fundamentally depend on large-scale computer calculations or huge random card pools should be modified.

Examples that may require physical adaptations:

- Generate a random card from the entire game.
- Choose a random card satisfying several hidden conditions.
- Extremely complex random-generation effects.
- Effects that require searching thousands of possible cards.
- Effects that rely heavily on invisible game-state bookkeeping.

These should be handled individually later.

# 4. Physical Game Assumptions

Initial physical Undercards rules should remain close to the digital game.

Expected components per player:

- 25-card deck.
- 1 SOUL.
- Artifact cards.
- 4 monster spaces.
- HP tracker.
- Gold tracker.
- Dustpile.
- Status markers.
- Buff/debuff markers.
- Generated/token cards.
- Dice where random selection is needed.

Generated cards should be treated as **real physical cards stored outside the main deck**.

Example:

```text
PLAYER DECK
├── 25 normal cards
├── SOUL
├── Artifacts
│
└── GENERATED / TOKEN POOL
    ├── Gaster Blaster ×4
    ├── Token A ×2
    ├── Token B ×3
    └── ...
````

Generated cards should normally return to the token/generated pool when they permanently leave the relevant game zones.

Exact rules can be refined later.

# 12. Card Renderer

Do NOT simply screenshot the existing Undercards web card at its small web resolution.

The renderer should be designed for printing.

Target physical card size:

```text
63 × 88 mm
```

This is approximately standard trading-card size.

At 300 DPI:

```text
63 mm ≈ 744 px
88 mm ≈ 1039 px
```

Therefore recommended base render size:

```text
744 × 1039 px
```

Potentially render slightly larger to include bleed.

Example:

```text
Card size:
63 × 88 mm

Bleed:
3 mm

Rendered document:
69 × 94 mm
```

At 300 DPI that is approximately:

```text
815 × 1110 px
```

Exact dimensions should be calculated properly in code.

# 14. Renderer Technology

Evaluate:

### Option A — HTML/CSS + Canvas Export

Pros:

* Easy to reproduce Undercards layout.
* Easy text layout.
* Easy preview.
* Works naturally in React.

Cons:

* Need to ensure proper high-resolution export.
* Browser rendering differences.

### Option B — HTML Canvas

Pros:

* Exact output dimensions.
* Strong control over rendering.
* Easy PNG output.

Cons:

* More manual text/layout work.

### Option C — SVG

Potentially the best option.

Pros:

* Resolution-independent.
* Excellent for print.
* Easy scaling.
* Easy text positioning.
* Can export SVG directly.
* Can rasterize to PNG at arbitrary DPI.
* Good PDF integration.

Cons:

* Requires slightly more custom renderer work.

Preferred direction:

```text
SVG-based card renderer
```

unless implementation proves inconvenient.

# 25. Random Effects

Physical conversion rules should eventually be documented.

Simple random targeting can use dice.

Example:

```text
4 enemy monsters:

1 = Slot 1
2 = Slot 2
3 = Slot 3
4 = Slot 4
```

For a d6:

```text
1 = Slot 1
2 = Slot 2
3 = Slot 3
4 = Slot 4
5–6 = reroll
```

Or use a d4 directly.

Random card-generation effects requiring huge card pools may need custom tabletop rules.

Maintain a list:

```text
docs/
└── physical-card-conversions.md
```

Example:

```text
CARD:
Example Card

DIGITAL EFFECT:
Add a random Rare monster to your hand.

PHYSICAL EFFECT:
To be determined.
```

Do not change effects until actually necessary.

# 41. Core Principle

Whenever deciding how to implement something, follow:

```text
Can the real Undercards behavior reasonably be represented
with cards, tokens, counters, markers or dice?

YES
→ Keep it 1-to-1.

NO
→ Create the smallest possible physical adaptation.
```

The goal is not:

```text
"Create a simplified game inspired by Undercards."
```

The goal is:

```text
"Make actual Undercards practical to play physically."
```

That distinction should guide the entire project.
